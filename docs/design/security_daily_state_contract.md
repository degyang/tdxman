# 证券逐日状态与修补原则

## 定义与判断

状态的键是 `symbol + trade_date`，不能以一个个股级状态代表全部历史。

| 字段 | 回答的问题 | 使用边界 |
|---|---|---|
| `trading_status` | 当天有无可确认的成交、停牌或未上市事实 | 有效 OHLC 和正成交量可证明成交；缺来源枚举不妨碍依据真实行情补状态 |
| `calc_status` | 现有逐日计算把该输入分到哪个类别 | 当前 `NO_TRADE` 还包含缺失/未确认输入，仅为统计排除分类，不能对外解释为确认停牌 |
| `limit_status` | 当前涨跌停统计口径是否适用、输入是否足够 | 不代表整条行情或其他因子可用性；BJ 的 `NO_LIMIT` 是当前统计范围排除 |
| `feature_state.status` | 当前派生发布是否与基础输入版本一致 | `READY` 不保证每个因子都有值；历史输入不足继续明确返回缺失 |

下载的 K 线、复权依据、财务及明确的源端事实属于基础数据。根据这些数据推断的交易状态、计算的复权因子和其他衍生结果属于 Enriched。物理表位置不代替逻辑分层。

## 转换原则

1. 有效、有限的正价格，满足 OHLC 高低关系，并且真实成交量为正，可以确定 `TRADING`。成交额的缺失独立报告，不否定已观察到的成交；记录 `derived:stored_ohlcv`，不捏造原始行情的供应商来源。
2. 只有明确的源端停牌/未上市证据才能确定相应状态。零成交量、空返回、超时、接口不支持、分页没有覆盖，都不能推出停牌或无交易。
3. 采集失败与覆盖不足写入任务报告；不得用本次失败覆盖已有真实成交或明确停牌事实。没有既有事实的日期可以保留 `MISSING`，不能补零行情。
4. 明确状态与真实行情冲突时，先核验源端日期、证券、单位和修订值。经核验可修正历史状态，保留前后值和证据；状态不是只准向前推进的流程标签。
5. 对无效行情、历史缺口和无法核实的停牌，保留具体缺失原因。计算层的统计排除不构成新的业务事实。

## 使用与落库后的依赖

- 消费者按所需字段、窗口和证据判断可计算性，不因无关字段缺失否定全部数据。五个市场交易日与五次有效成交观察是不同算法，必须明确口径。
- 缺因子不补零、不自动重新分配权重。确认停牌的零量处理也必须符合该指标契约。
- 基础数据有实际变化后，依赖的逐股指标、市场/板块汇总及缓存版本必须一并处理并验收，不能把落库当成完工。
- 状态从空值规范为 `TRADING` 时，只有逐条验证现有计算分类不变、成交样本选择不变、数值字段不变，才能复用已有 Enriched。已有缺失因子继续缺失，同时更新逐股与市场发布戳；不受影响的板块计算输入与结果保持原值。其余情况必须使用完整依赖重算入口。
- 无变化重跑不重写、不增加版本。状态批量维护只改一个 `features.sqlite` WAL 文件，禁止借维护入口修改行情、因子或数值派生列；数值修补仍走具有持久化发布意图的统一日更事务。

## 十年检查工具

`scripts/ops/audit_repair_daily_states.py` 使用明确起止日期（最长 3660 日），按证券主键范围检查全部现有日 K 和逐日事实，输出缺状态、行情矛盾、无效输入、缺 K 线和计算分类矛盾。已确认无交易的遗留占位 K 单独列示，不当成真实零价成交。

该检查是**本地已有记录的完整状态审计**，不能证明每个证券上市以来的所有交易日已覆盖。没有生命周期和完整交易日历依据时，不把历史没有记录的日期伪装成已核实缺口。源端补取实际覆盖和无法取得的日期逐项保留。

修补前必须建立一致恢复点，检查 SQLite 并通过公开接口读回；证据与报告放池外。安全状态规范化逐证券原子提交，失败后重跑即可续修；真实行情修补使用完整日更事务并验证 Enriched，结束后重新扫描整个窗口。

### 运行方法

安装配套 wheel 后可在任何目录运行：

```bash
# 完整只读检查，不修改生产数据
python -m aspool.sqlite_state_audit \
  --root /path/to/data --start 2016-10-01 --end 2026-09-30 \
  --report-dir /path/outside/pool/audit

# 先创建一致恢复点，再修补空状态并补取异常证券的历史行情
python -m aspool.sqlite_state_audit \
  --root /path/to/data --start 2016-10-01 --end 2026-09-30 \
  --report-dir /path/outside/pool/repair \
  --repair --source-repair --prepare-recovery \
  --recovery /path/outside/pool/recovery
```

中断后重跑同一范围，使用既有 `--recovery`，省略 `--prepare-recovery`。已完成状态修补为 no-op；每次运行报告描述该次实际检查与改动，逐证券数值校验回执追加保留。源端补取每个异常证券请求最多 3000 根日 K，记录实际返回范围；未返回目标日期不构成停牌证据。

报告输出：`report.json`、`normalization-receipts.jsonl`、`anomalies-before.json`、`anomalies-after.json`、`source-observations/`。`completed_with_unresolved` 表示扫描结束但仍有未解决输入，不表示数据完整。普通已确认停牌的遗留占位 K 单独列示。

全窗口审计会明确读取冷历史，属于专门维护任务；日常增量不会自动调用。每证券规范化最多 5000 条输入、最多 25000 条发布变化，已有板块结果因计算输入等价而复用；实际行情变化走完整依赖更新入口。
