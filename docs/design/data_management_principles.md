# 行情数据治理：增量更新、历史修订与可恢复性

日期：2026-09-27。性质：研究与设计建议，未实施生产迁移、修复、重算或删除。

## 1. 结论与研究边界

日常只改变几天的数据，应默认按实际变化增量处理。但“下载增量”只是起点：存储写入、派生计算、缓存失效、发布和备份也要有各自的边界。一个环节使用全局版本或全历史文件，就可能把局部变化放大。

建议采用的总原则是：**以真实变更为起点，以业务依赖确定影响范围，以一致版本发布结果，以恢复目标决定保留范围。**

这不是要求所有操作都变成增量。首次建库、规则升级、无法确定影响边界的修复，以及成本更低的批量重建，仍应允许全量路径；但它们应有明确原因、成本预估和独立执行入口，不能成为日常更新的隐式副作用。

本研究核对了增量计算论文、Apache Beam、DuckDB、Iceberg、Delta Lake、dbt、PostgreSQL 官方资料、Google SRE 与时间建模资料，并回看 aspool/Fundwise 代码。外部资料支持的是一般机制；下文针对本项目的设计与优先级属于结合代码后的建议，尚未通过实现验证。

当前池此前盘点约 4.1 GiB，日线文件逻辑体积约 1.5 GiB。主要问题是变化传播和恢复管理的粒度，而非已经需要分布式“大数据平台”。沿用 DuckDB + Parquet 可以承载下一阶段整治；没有证据支持此时引入 Spark、Kafka 或迁移整套湖表格式。

后续 [日线存储结构专项评估](../daily_storage_architecture_assessment.md) 已完成真实只读查询及隔离写入实验。
结果支持现在启动日线存储与访问层专项重构，将物理存储整改由候选优化上调为明确工作项；仍不推荐机械地普遍拆小文件或全面平台化。
具体布局选择及实验边界以该专项报告为准。

## 2. 当前链路为何会“几天变化，历史都动”

| 环节 | 代码或观测证据 | 含义 |
|---|---|---|
| 数据获取 | `src/aspool/tdx_online.py` 对已有证券重叠抓取近期数据，新证券另行回补 | 网络获取已经有增量机制，不能将整个链路描述成每次重新下载全部历史 |
| 日线合并 | `src/aspool/daily_storage.py:153` 读取整个证券文件；`:202` 比较变化；`:235` 替换输出文件 | 无变化时已有跳过机制；有变化时仍存在物理文件写入放大 |
| 失效标记 | `daily_storage.py:233` 从最早 touched 日期标记已发布后缀；`limit_events.py:956` 主要记录日期和原因 | 尚未按证券与字段细分依赖，保守边界会覆盖不必失效的结果 |
| 补齐与重算 | `enrichment.py:416` 默认近期窗口；`:473` 再请求起点前 120 个自然日；`limit_events.py:1191` 明确整段后缀重算、不提前退出 | 近期补齐窗口与实际派生计算窗口不同，重叠窗口进一步放大工作量 |
| 计算读取 | `limit_events.py:1234` 附近遍历日线日期构建市场轴，`:289` 读取证券历史供窗口使用 | 请求范围窄不意味着底层读取同样窄；应单独测量扫描量与计算量 |
| Fundwise 缓存 | `fundwise/regime/freshness.py:25` 将全池文件大小、mtime、coverage 等混入 revision；`data/regime_events.py:43` 用它校验各月缓存 | 一处来源变化可能使所有月份缓存失效；仅改变编码或文件布局也可能失效 |
| Fundwise 业务口径 | `fundwise/regime/service.py:373` 用结束日名称/ST 快照排除整个计算区间；板块使用 SDK 当前成分快照 | 某些最新维度变化确实可能影响整个历史展示，不能靠缩小文件范围消除 |
| 日线与派生耦合 | `src/aspool/pool.py:83` 将日期事实与已发布限价参考价覆盖进日线字段；参考派生 stale 时可能不再提供该参考价 | 要区分独立来源事实与推导事实；派生失效也可能影响基础接口字段可用性 |

Fundwise 路径以上均相对于 `/mnt/d/Workstation/Projects/fundwise`。这是一份代码检查，不是本轮端到端性能测量。

已有 [数据观测](evidence/data-retention/20260927-observation.json) 在 2026-09-27 00:34:55（上海时间）记录：限价覆盖 1,296 日，其中 605 日 stale；这不证明所有基础字段、交易会话和证券覆盖均完整。`v8` 是规则版本，不能唯一标识整个数据池的某次快照。

## 3. 首先分开五种粒度

| 粒度 | 要回答的问题 | 示例 |
|---|---|---|
| 逻辑变更 | 哪个事实真正变了？ | 某证券某日 amount 修正 |
| 依赖读取/计算 | 为算对结果，需要哪些输入与前置状态？ | 读取前置窗口，计算受影响当日汇总 |
| 物理写入 | 存储最少需要重写什么？ | 一个 Parquet 文件或一个数据库事务 |
| 一致发布 | 哪些结果必须一起对外成为新版本？ | 当日 events、summary、coverage、exceptions 及输入版本 |
| 恢复保留 | 为恢复哪些时点，需要保留哪些对象？ | 一致基线、后续变更、规则与来源凭据 |

“多读几天用于预热”不等于“多改几天历史”；“重写一个文件”不等于“文件里所有日期都发生业务变化”；“旧文件不再供当前查询”也不等于“已经失去恢复价值”。这五种范围不能共用一个起止日期或一个全局 dirty 标记。

## 4. 十二条指导原则

### 原则一：变更应成为可记录、可重放的对象

dbt 的增量模型要求明确筛选增量记录，并在需要更新已有行时配置稳定键。Debezium 则将初始快照与后续已提交的行变更分开。这些实践的共同点是显式识别变化，而非把“本次扫描范围”当成“本次修改范围”。[dbt 增量模型](https://docs.getdbt.com/docs/build/incremental-models)、[Debezium PostgreSQL Connector](https://debezium.io/documentation/reference/stable/connectors/postgresql.html)

本项目建议先建立轻量变更清单，至少包含：`change_id`、证券、交易日、变化字段、插入/更新/删除类型、来源、发现时间、原版本与新版本、原因；旧新值可记录在变更表，也可指向可恢复的版本对象。不要只留下一个最早变化日期。

同一批次重试必须幂等；实际值未变时不生成新的业务修订。来源返回空集合、接口失败、停牌和明确撤销记录必须分别表达，不能把“这次没取到”解释成删除。

先实现这个元数据基础通常比先改目录结构收益更大：它同时服务重算、缓存、审计和恢复。没有可靠变更清单时，应保留现有保守失效机制，不能为了性能漏报变化。

### 原则二：热点窗口是调度策略，不是历史真相的边界

Beam 区分事件发生时间与处理时间，并用 watermark 和迟到处理策略管理延迟到达的数据。这里借鉴时间语义，不要求引入流计算引擎。[Beam：Watermarks and late data](https://beam.apache.org/documentation/programming-guide/#watermarks-and-late-data)

行情同样至少有交易日、上游修订时间（若可得）、本地发现时间、发布时间。今天发现三年前的错误，它是今天的工作，但修改的是三年前的事实。

建议分三条工作路径：日常刷新近期热点；按证券/日期/字段受理任意历史修订；规则或数据结构迁移使用独立重建任务。热点长度应依据修订延迟分布、供应商修订习惯和漏检代价确定。窗口外修订仍可由来源通知、明确修复单或低频核对发现；如果来源没有变更通知，只扫热点不能证明冷历史永远未变。

“历史稳定”应理解为通常少写、例外可修订，而不是禁止更正。新上市证券的历史初始化也应独立于存量证券日常刷新。

### 原则三：重算边界取决于依赖闭包，不能只按日期切一刀

增量视图维护研究关注如何从输入差异推导输出差异；并非任何计算都能在常数成本下完成。DBSP 给出了可组合的增量计算框架，是这里区分依赖类型的理论参考。[DBSP 原论文](https://arxiv.org/abs/2203.16684)

下表是应建立的依赖规则示例，具体字段关系仍需以本项目算法逐项确认：

| 实际变化 | 应调查的影响范围 | 允许停止/不传播的条件 |
|---|---|---|
| 单日成交额 | 当日事件金额、成交统计、使用该金额的排名与窗口指标 | 限价判定不依赖 amount 时，不应使价格型限价事件失效 |
| 成交量 | 当日成交统计及依赖它的后续量比窗口 | 超出明确的滚动依赖窗口，且无其他递归依赖 |
| 收盘价、前收盘价 | 当日涨跌/限价判定、依赖前价的后续有效观测、滚动指标、连板状态 | 分别使用窗口界限和递归状态收敛条件 |
| 插入/删除一个历史会话或行情点 | 该证券的前后邻接关系、窗口成员、连板状态；若是市场日历则范围更广 | 不能套用“只影响次日”，需要重建实际会话关系 |
| 当日一个证券的事件变化 | 当日全市场计数、最高板、梯队、板块排名 | 可以重算受影响整日截面，不由此推出重算全部年份 |
| 日期化 ST/交易状态修订 | 对应有效期的资格与规则，并沿下游依赖传播 | 以实际业务生效区间为边界 |
| “当前 ST/当前板块”快照变化 | 所有引用该快照的历史结果可能改变 | 这是当前业务口径的真实依赖；需版本化快照或另立历史口径 |
| 限价规则升级 | 新规则适用范围及其下游结果 | 除非证明不受影响，否则使用明确的迁移重算 |

例如，按证券有效观测计算的 MA20 中，一个收盘价通常影响本条及其后 19 个观测的均值；这是观测序号，不一定是 20 个自然日。连板属于递归状态，不能用同样的固定窗口替代。删除当日最高板证券后，寻找新最大值可能需要检查该日其他证券；这属于必要工作，而非实现缺陷。

### 原则四：递归传播在完整状态收敛时终止

设状态转移为 `S[t] = F(S[t-1], X[t], rule)`。历史修订后，只有当某个边界的新旧完整状态相同、后续输入与规则相同，且状态已包含影响未来所需的全部信息，才可复用后续结果。

连板状态不能只比较显示出来的板数，还可能包括未知/缺失标记、边界状态、上一有效观测和上市规则状态。显示值碰巧相同，不代表未来状态相同。若后面还有第二处修订，只能复用到第二处修订前，再继续传播。

工程上先实现单证券状态传播，再汇总受影响的日期集合，重算这些日期的市场/板块截面；保留无可靠检查点时的完整后缀回退。当前 `compute_limit_events` 明确采用完整后缀方案，这是正确性保守策略。优化必须先证明与全量参考结果一致，不能直接删掉 stale 或增加武断的传播天数上限。

### 原则五：明确“历史当时状态”和“今天重新解释历史”

时间建模区分事实何时有效，以及系统何时得知该事实。同一个历史日期可能因后来的信息得到修订，而当时展示过的结果仍需可解释。[Martin Fowler：Bitemporal History](https://martinfowler.com/articles/bitemporal-history.html)

本项目至少有三个不同问题：当日有哪些股票处于 ST；今天的 ST 名单是什么；当时那次 Regime 运行使用了哪一版名单。当前代码用结束日 ST 快照过滤历史，板块也采用当前成分，这可以是产品选择，但它天然允许历史结果随着最新名单变化。

应在结果中记录维度快照版本与解释口径。如果未来需要历史时点分析，应建立有效期事实，而不是用今天名单静默代替。无需立即建设完整双时态数据库；记录交易日、发现/发布时间、来源版本和运行所用维度快照，就能先解决多数可追溯问题。

### 原则六：逻辑版本与物理文件版本必须分开

Delta Lake 将只重排文件、不改变数据内容的 compaction 与业务数据变化区分。这说明物理维护不应天然等价于结果失效。[Delta Lake 并发与 compaction](https://docs.delta.io/concurrency-control/)

Fundwise 当前用全池文件指纹作为保守变化提示，在缺少上游版本接口时有合理性。但它既放大了失效范围，也不是不可变数据快照：读取前后指纹检查能发现许多变动，不能自动提供多表一致读取。

建议分别表达 `source_revision`、`rule_version`、`schema_version`、`publication_generation` 和存储布局版本。月份缓存依赖其涉及的行情、事件及前置状态修订；使用当前 ST/板块的结果再附加维度快照版本。无关月份的变化不应改变该缓存的依赖标识。

版本应随可靠提交维护，不应每次查询都重新全池计算内容哈希。上游未提供可靠细粒度修订前，不能简单停止检查文件变化。逻辑数值未变但来源证据改变时，也要根据消费者是否依赖该证据决定版本与失效范围。

### 原则七：分区以总成本选择，避免把小变化变成海量小文件

DuckDB 文档强调 Parquet 文件和 row group 大小会影响并行、裁剪与开销；分区过多也会产生昂贵的小文件管理成本。它给出的通用分析负载尺寸建议不应直接变成本项目的硬门槛。[DuckDB 文件格式性能](https://duckdb.org/docs/current/guides/performance/file_formats)、[DuckDB 分区写入](https://duckdb.org/docs/current/data/partitioning/partitioned_writes)

本次 [文件大小观测](evidence/data-retention/20260927-file-sizes.json) 为 7,288 个日线文件，逻辑体积约 1,513.87 MiB，平均约 212.71 KiB、中位数约 170.62 KiB，最大约 0.58 MiB。它们已经很小。机械地再按“证券 × 年/月/日”拆分，可能减少局部重写，同时增加文件打开、扫描、备份和迁移复杂度。

| 候选方式 | 优点 | 成本与采用条件 |
|---|---|---|
| 保持现有证券文件，先改善变更/读取/失效 | 改动小，保留成熟读取链路 | 仍有文件重写；应先测它是否真是主要瓶颈 |
| 近期变化进入事务表，定期并入 Parquet | 局部 upsert 清晰，可批量合并冷历史 | 读路径需要覆盖、删除与去重规则；增加双层一致性工作 |
| 按时间聚合全市场或适当证券分桶 | 有利于全市场窗口查询和近期批量写入 | 单证券历史读取可能变差，需要统计裁剪与基准验证 |
| 保留证券分区，仅对确有大文件者分年 | 可控迁移，不普遍制造更小文件 | 需兼容布局与跨年更新；现有单证券文件规模尚未证明收益 |

冷热划分可以先是调度和写入策略，不必立刻成为新的物理目录。压实、重编码与快照清理也应分别执行。选型目标是读取量、重写量、文件数量、内存、恢复成本和工程复杂度的综合成本。

### 原则八：有界工作仍需一致发布，单文件原子替换不够

Iceberg 使用版本化元数据和原子提交使读取者看到一致的表快照；Delta 的写入过程包含读取、暂存、冲突检查和提交。借鉴的是发布协议，并不意味着采用其中任意一个就自动得到跨所有表的事务。[Iceberg 规范](https://iceberg.apache.org/spec/)、[Delta 并发控制](https://docs.delta.io/concurrency-control/)

建议的本地流程为：固定输入版本 → 生成变更清单与计算计划 → 写候选文件/表 → 校验 → 提交发布代次 → 延迟回收旧对象。涉及一个业务发布的行情引用、日期事实、events、summary、coverage 和 exceptions 必须能关联到同一组确定的输入与输出版本。

现有 DuckDB 与外部 Parquet 不会因为分别写入成功而天然成为一笔事务。可先通过单写入协调、不可变候选文件、数据库发布清单和故障恢复记录实现；读者通过发布清单固定版本。提交前验证输入代次没有变化，失败后继续保留可识别的旧发布或明确的 stale 状态。具体协议需要故障注入验证。

避免多个维护进程各自改库、各自替换文件。DuckDB 的原生写入并发模型也要求注意进程边界，不能假定任意多进程写入都可自动协调。[DuckDB 并发说明](https://duckdb.org/docs/current/connect/concurrency)

### 原则九：完整性是数据契约，不等于 stale 清零

stale 表示派生与其输入/规则的关系是否过时；缺行、重复键、缺值、单位错误和未知交易状态是不同问题。1,296 日已发布或五年读取完成，都不能证明每个证券的每个必需字段有效。

建议为每类数据明确键、字段单位、价格调整口径、NULL 含义、来源优先级、覆盖范围、上市/退市与停牌处理，以及消费者允许的降级。`amount`、`pre_close`、`is_st` 等字段还需区分原始值、独立日期事实和算法推断值。

尤其要检查日线公开接口依赖限价推导参考价的情况：应明确来源与失效域，避免基础事实和派生结果在解释上相互证明。未知必须保留为未知，不能为了填满覆盖表而编造 0 或停牌状态。

来源、转换活动和输出之间的关系应可追溯。W3C PROV 提供了通用概念；本项目用清单与运行记录即可起步，无需先建设独立血缘平台。[W3C PROV Overview](https://www.w3.org/TR/prov-overview/)

### 原则十：备份策略从恢复目标倒推，增量备份并非总是更好

Google SRE 将恢复能力作为备份设计的出发点，并指出渐进式损坏可能很晚才被发现。PostgreSQL 也明确提醒，备份清单与校验和检查不能替代实际恢复验证。[Google SRE：Data Integrity](https://sre.google/sre-book/data-integrity/)、[PostgreSQL：pg_verifybackup](https://www.postgresql.org/docs/current/app-pgverifybackup.html)

本项目应先定义：允许损失多少最新数据（RPO）、允许多久恢复服务（RTO）、需要追溯多远才能覆盖延迟发现的错误、是否需要恢复某个证券或某些字段，以及来源历史能否重新取得。

“基线 + 增量”能减少重复复制，但增加依赖链与重放成本；一个关键中间段丢失可能破坏后续恢复。PostgreSQL 的连续归档展示了基线与连续日志共同构成恢复链的要求；这里仅借鉴这一约束，不代表 DuckDB 已具备同样的 PITR 能力。[PostgreSQL 连续归档](https://www.postgresql.org/docs/current/continuous-archiving.html)

对于约 4 GiB 的本地池，定期一致全量快照可能比自研复杂增量恢复系统更便宜、更可靠。可保留较少完整基线，并记录日常必要变更；具体频率以复制成本和恢复演练决定。压缩备份与原始文件放在同一磁盘，能帮助操作回滚，但不能覆盖该磁盘损坏。

现有旧日线归档与 v7 数据库来自不同操作时点，不能直接当作一致整池恢复点。前轮无损重压缩的 SHA 一致证明内容没变，不证明整池可恢复。应在独立位置恢复候选基线，验证公开字段、发布关联与 Fundwise 最小读取链路。

### 原则十一：删除依据是无必要引用且恢复仍成立，年龄只是一个条件

Iceberg 分开处理快照过期、孤儿文件和小文件压实，并提醒清理不能误删仍在进行的写入。Delta VACUUM 同样要求保留期覆盖长事务和滞后消费者。[Iceberg 维护](https://iceberg.apache.org/docs/latest/maintenance/)、[Delta VACUUM](https://docs.delta.io/delta-utility/)

适用于本池的删除条件应同时满足：不属于当前发布；不被保留恢复点或重放链引用；不被运行中的读写任务引用；不属于未结问题或需要保留的唯一来源证据；且达到已确定的保留期。必要时先退出服务引用并隔离，再做最终删除。仅移动到同盘目录不算释放空间。

需要按用途给对象定性：生产历史是业务输入；原始来源凭据可能不可再生；派生导出在输入、规则、依赖均保留时才可再生；缓存通常可丢弃；运行报告中既可能有普通日志，也可能有尚未入库的唯一候选数据；备份用于恢复特定历史状态。目录名 `reports` 或版本号 `v6` 不足以决定删除。

对先前方案的修正：连续 7 个交易日更新成功只能作为运行观察，不能证明更久以前的错误不会晚发现；保留一个“最新正确基线”也未必能替代修复前原始证据。成功日志 30 日只能作为待评估默认值。退役恢复点应依赖明确恢复目标、引用检查、问题闭环与恢复演练，不能仅以固定天数触发。

### 原则十二：用正确性与放大成本一起验收

核心正确性条件是：同一输入快照、规则和维度口径下，增量结果等于完整参考重算结果。数值误差容限应按字段契约规定；键、事件标记、连板状态和发布关系应精确一致。

至少覆盖：新日追加、重复执行无变化、旧日改单字段、删除/插入、跨年、上市与 ST 边界、缺失变未知、多个不连续修订、递归收敛、规则升级、发布前失败、写文件后元数据未提交、并发输入变化。只验证“返回行数一样”不足以证明增量正确。

每次任务建议记录以下成本：

| 指标 | 要揭示的问题 |
|---|---|
| 实际变更键数、字段数、日期/证券范围 | 本次业务增量究竟有多大 |
| 扫描字节/行数与必要依赖读取规模 | 是否仍为局部更新扫描全池 |
| 重写字节与变更逻辑数据量 | 存储布局的写入放大 |
| 重算输出数与可证明受影响输出数 | 是否由粗粒度 stale 扩大计算 |
| 缓存失效数与受影响依赖范围 | 是否仍用全局 revision 失效所有月份 |
| 新增备份字节、保留总量、实测恢复耗时 | 增量维护是否转移成备份与恢复负担 |
| 峰值 RSS、临时磁盘、总耗时、任务积压 | 是否在资源预算内稳定完成 |

分母为零时单独记录绝对开销，不输出无意义的放大倍数。避免用压缩文件字节直接除以未压缩行字节作未经说明的比较。

P0 的五年读取峰值 RSS ≤ 2 GiB 是特定读取链路的验收，不自动涵盖补齐、维护、重建和备份。后续应分别给日常更新、历史修复和规则迁移设置资源预算与增长基准。数值阈值需要实际基准测量，本研究不虚构性能承诺。

## 5. 三类任务如何执行

| 场景 | 正常路径 | 扩大范围的理由 |
|---|---|---|
| 新增一个交易日，近期旧值未变 | 热点拉取 → 比较 → 写新增/真实变化 → 带必要前置状态算新结果 → 一致发布；无依赖变化的历史缓存继续可用 | 当前 ST/板块快照变动等业务依赖；不能把这些隐含变化漏掉 |
| 更正三年前某证券一天的收盘价 | 明确历史修复单 → 记录旧新值 → 读取前置状态 → 有限窗口及递归传播 → 重算受影响日汇总 → 发布受影响范围 | 状态未收敛、检查点缺失或规则无法确定时，回退完整依赖后缀 |
| 限价算法 v8 升级 | 明确适用历史 → 固定输入版本 → 分批构建新结果 → 对比验收 → 切换发布 → 保留必要回退版本 | 规则语义本就改变整个适用范围，批量历史重建可能是正确且更经济的选择 |

已有 605 日 stale 应根据造成失效的实际修复、输入与规则重新确定计划。不能因为希望采用热点更新，就只刷新最近几天或直接清除剩余标记；也不能仅凭 605 这个数字断言所有基础历史必须重新下载。

## 6. 建议实施顺序与交付门槛

1. **先测量并建立变更记录。** 给现有链路增加实际变化与读写/重算范围观测，形成字段依赖表、业务时间口径和历史修复入口。交付门槛：重复输入不制造业务修订，任意历史修复可定位，现有正确性不退步。
2. **补齐逻辑版本与一致发布。** 给消费者可靠的数据修订信息，记录输入版本、规则、维度快照和输出代次；校验失败保持可识别状态。交付门槛：故障后读者不会把混合代次当成完整新发布。
3. **收窄失效与计算传播。** 基于字段/证券/日期依赖实现有界计算、状态收敛与月份缓存复用，保留全量参考和保守回退。交付门槛：与参考重算一致；无关历史缓存可复用；原五年读取 RSS 验收继续成立。
4. **按瓶颈决定存储改造。** 只有测量显示文件重写或扫描仍主导成本，才试验热数据事务表、时间聚合或选择性分年，并比较日常更新、历史修复、全市场窗口与单证券查询。交付门槛：收益覆盖迁移、读取兼容和恢复成本。
5. **建立恢复基线后治理保留。** 定义恢复目标、验证完整恢复与局部恢复、梳理未结证据及引用，再执行恢复点退役和日志滚动。交付门槛：删除后仍满足既定恢复范围；空间收益扣除新基线成本后报告。

清理既不应等待所有性能优化完成，也不能替代恢复验证：可独立处理已确认可再生、无引用的缓存和冗余副本；当前两个大旧备份仍需满足恢复与证据条件。
