# Regime 数据依赖与 aspool 清理方案

日期：2026-09-27。状态：方案，尚未执行新增删除、迁移、补数或重算。
范围：`/home/ubuntu/.aspool/reports` 的生命周期整理；不通过裁剪生产行情来回收空间。

## 结论

Fundwise 的需求说明与当前代码一致。此前“只需当前 v8”的说法只适用于限价派生版本，不能代表完整数据需求。
Regime 还需要多年股票日线、上证指数、日期事实及板块成分；历史预热和后续每日派生也必须持续可用。

v8 实际是规则版本 `cn-a-share-limit-v8`，不是一个可单独保留即可运行的报表目录。
生产接口通过逐日 `batch_id` 与 publication 关系读取事实。清理 `reports` 既不能修复 stale，也不能代替补数、重算和重新发布。

建议：保留生产数据与未结问题证据，先完成基础字段/覆盖和派生验收，再退役旧恢复点。
当前不安排 GiB 级直接删除。建议采用“当前发布结果 + 满足恢复范围的已验证基线及必要变更 + 未结问题证据”的保留策略，
替代无限累积历史副本；基线数量由恢复目标决定，不能预先限定只有一个。本方案尚未替换原 v7/v8 两版保留约定。

后续深度研究见 [行情数据治理原则](data_management_principles.md)。研究修正了初版中的两个默认建议：
连续 7 个交易日成功不能单独作为旧备份退役依据；30 日日志保留期也需要结合错误发现延迟和引用关系确定。
原始 observation JSON 保留当时提出的条件作为记录，后续执行以本文件修订后的条件为准。

## 需求与代码核对

| 需求 | 当前读取方式 | 清理约束 |
|---|---|---|
| 多年股票日线 | `fundwise/data/aspool_backend.py:8` 请求 close、pre_close、pct_chg、amount、is_st、turnover_rate 和证券/日期键 | 保留日线全历史、字段来源及补充事实；不能只保留事件日或五年涨停明细 |
| 名称与 ST 排除 | `fundwise/regime/service.py:373` 单独读取末日 name/is_st，再按当前快照排除证券 | 保留名称、日期 ST 及来源；当前口径不等于逐日历史 ST 排除 |
| 指数及预热 | `aspool_backend.py:72` 读取上证指数；`service.py:348` 按实际指数会话定区间 | 每个股票读取窗口向前取 60 个自然日，另设 lookback=260；不能误写为 60 个交易日 |
| 限价派生 | `aspool_backend.py:121` 读取 summary、coverage、events、exceptions；`regime_events.py:63` 优先使用有界事件金额接口 | 保留当前发布关系、批次、scope、参考价、连板边界和 stale；历史重算依赖也要保留 |
| 概念/行业成分 | `fundwise/data/regime_membership.py` 使用 tdxman SDK，并在 Fundwise 缓存 | 不属于 aspool reports；本方案不清理 Fundwise 缓存，也不改分类口径 |

默认起点会考虑已有结果、限价发布起点和至少约 500 个指数会话，并可显式请求更长区间。
假如业务起点为 2021-05-27，第一窗口股票预热起点为 2021-03-28；这只是该计算窗口的最低读取需求，
不能据此删除更早历史，因为还有其他调用方、显式长区间与上游派生依赖。

aspool `enrichment.py:473` 还请求补齐起点前 120 个自然日的限价重算；
`limit_events.py:1202` 从最早请求日起计算到最新受影响发布日期，当前没有状态收敛后提前停止。
因此不能将“日常增量”为主推导成“以后永不需要大范围历史重算”。

## 分阶段执行计划

1. **建立清单（本轮已完成）**：记录路径、用途、当前大小、依赖与待清理条件；保留 2026-09-27 备份无损压缩记录。
   没有发现可以直接判定无用的大文件，本轮不执行新增删除。
2. **数据验收与问题闭环（后续独立工作）**：
   - 明确 Fundwise 要保留的历史范围，连同每段预热，逐证券按上市/退市和交易状态核对日期覆盖。
   - 按有界窗口通过公开接口检查 close、pre_close、pct_chg、amount、turnover_rate、is_st、末日 name：
     缺值/非法值、重复键、单位及来源覆盖；不要将缺会话直接判成停牌或以 0 补齐。
   - 核对上证指数日期、close 和会话边界。针对 522 条候选及来源差异形成逐项处理结果。
   - 对受影响派生补齐/重算并发布；消费窗口 stale 清零，summary/coverage/events/exceptions 批次一致，
     unknown/invalid 的剩余原因与下游处理口径有明确记录。仅将 stale 改为 false 不算修复。
   - Fundwise 完成多年市场与主线真实链路验收、来源修订检测和资源验收。
3. **准备替代恢复基线**：在同一稳定时点保留生产数据库与相应行情/事实清单，必要时保留变更前文件；
   在独立位置恢复并验证公开接口。现有旧日线备份与 v7 数据库来自不同操作时点，不能直接声称它们组成一致整池快照。
4. **观察与退役（建议门槛）**：先定义可接受数据损失、恢复耗时及历史追溯范围，结合错误发现延迟确定保留期；
   验证替代基线及必要变更链可恢复，候选对象无当前发布、运行任务或未结问题引用，且不损失必须保留的修复前来源证据。
   连续 7 个交易日更新成功可作为额外观察，不能替代上述条件。满足条件后再按候选清单退役旧日线备份、v7 库备份和已闭环导出。
   如果业务仍要求回到修复前原始数据，则冷归档旧备份，不删除它的最后一份副本；可能需要保留多个恢复点。
5. **日常滚动**：成功运行日志的 30 日窗口待追溯需求评估后采用；失败和未结证据不按时间自动删。
   每次清理保存路径、大小、SHA256、原因与验证结果，且不能破坏保留恢复点的依赖链。

第 2—4 步是后续计划，并非本轮已经执行或已经通过的验收。
备份冷归档若仍在同一磁盘，只改变目录位置，不能记为全机空间释放；真正回收本机空间需外部存储或删除冗余副本。

## DG-01 变更链的保留边界

新增 `change-state/preparing/**`、`pending/**` 是未结准备/恢复依赖，不能按年龄删除；pending 缺必要对象会阻断公开读。`applied/**` 的 manifest/逐行旧新值证据与 catalog 内业务、coverage 元数据日志和逻辑序号共同构成变更链，snapshot/manifest 必须纳入 `change-state/**`。保留恢复点、活动任务及未结问题引用检查也应包括这条链；没有新增按天自动清理工具。

协议自身仅在确定已提交、或确定 preparing 从未进入发布队列时释放冗余临时 redo，保留行证据与状态；这不是旧历史/恢复点退役，不保留每代完整冷历史。`reports/changes` 和任务 JSON 仍是观测，不独自构成事务恢复链；不能因 JSON 成功存在或连续若干日无错误而删准备/唯一来源证据。本轮不执行生产清理，具体故障与恢复语义见 [DG-01 实施报告](../achievements/dg01_implementation.md)。
