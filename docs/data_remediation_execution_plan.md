## 1. 目标、范围与权威入口

本方案将数据治理研究和存储专项评估转为可执行任务。主要整改对象是 **tdxman 的 aspool**；Fundwise 是消费方，配套适配数据修订、缓存和联调验收。保持已有公开读取契约、行情单位及 Regime 业务口径。

完成目标：日常更新围绕实际变化执行；历史修订有明确范围和原因；读取、发布和恢复使用可解释的版本；多年日线增长不再迫使每次热点操作遍历和重写全部冷历史；旧报告与备份按证据和恢复价值退役。

已落地方案、POS 项目记录、DG-00 工程基线、DG-01 完整工程实现与隔离验证及 DG-02 Parquet 访问边界；DG-04 已完成具体授权的生产修复与重新发布；DG-03 候选实现和隔离试验正在推进，尚未实施生产迁移或删除。本文件维护任务状态、依赖、验收与回退要求；执行时更新本文件并链接证据，不在 POS 再维护一套独立任务状态。

## 4. 任务规格

### DG-00：冻结可核验基线，定义恢复与数据契约

工作：重新查询覆盖、stale、批次、日期事实及字段可用性；清点消费者、现有写入入口与锁；为修复和迁移保留一致的输入版本和恢复点。这里的“冻结”可以是受协调生成副本，不要求长期停止日常更新。

合同至少包含：日线唯一键、价格调整口径、成交额与成交量单位、NULL 含义、来源优先级、ST/交易状态有效时间、ETF/股票范围、指数会话、派生 unknown/invalid 的消费规则。

记录可接受最新数据损失、恢复耗时、历史追溯范围与错误发现延迟；尚无数值时列为待确定，不能使用任意 7/30 日替代。完成完整恢复和指定证券/日期恢复的最小演练；旧日线归档与 v7 库不自动构成一致快照。

交付：`baseline.json`、`data-contract.md`、`consumer-inventory.md`、`recovery-plan.md` 和演练结果。

验收：公开接口能读取恢复副本；行数/键/关键字段和发布关联与基线相符；已知缺口与未知项单列；可回答恢复点覆盖哪些对象、时间和输入版本。

### DG-01：统一真实变更和成本记录

修改入口：`daily_storage.merge_daily`、`enrichment._publish`、在线/离线导入、quote 和日期事实写入；以 DG-00 入口清单为准，不能遗漏旁路。

变更记录包含证券、交易日、操作类型、变化字段、来源、原因、输入/输出逻辑版本，以及旧值或可恢复旧对象引用。区分无变化、上游缺失、接口失败、明确删除与撤销，重试须幂等。

输出同一任务的真实变化数、候选文件/行、实际扫描/重写范围、重算范围、缓存失效范围、耗时、RSS、临时空间和锁等待。指标无法精确测得时标明代理量，不把文件大小或 SQL 返回行数当作设备 I/O。

验收：同样输入第二次执行不重写业务数据、不增加 stale、不改变业务 revision；源故障不被解释为删除；每次扩大影响范围能追溯到变化及规则。尚未完成依赖验证的字段保持保守失效。

首批 `981ab5f` 已由协调者集成 main/feature；`f949dbc` / `30870a5` 的首批缺陷结案保留原 [审查证据](data_remediation_first_batch_review.md)。本轮 DG-01 剩余实现覆盖 merge/enrichment、在线/离线/free-stockdb、quote/快照、BaoStock 三类事实、index/coverage 与 universe scope，补齐真实变化、内部业务/元数据修订、逐行有界证据、文件准备后前滚、catalog 原子日志/coverage/stale/聚合及任务成本。完整差异经独立审查，修复恢复版本/manifest/父目录持久化、源故障/重试、UTC TTL、范围失效与成本记录问题；见 [审查报告](data_remediation_dg01_review.md) 和 [最终摘要](evidence/data-remediation/20260927-dg01-review/validation.json)。`bbb50b0` + `5b42c52` 已由协调者集成 main；生产池状态仍未变更。

无变化承诺针对源更新/补齐及其自动调度；协调者已明确确认显式 `compute_limit_events` 保留强制重算/重新发布语义，派生依赖/发布修订仍归 DG-05/06。单文件原子替换与 catalog 事务之间、多文件任务不是整体事务：pending 阻断公开读，源 writer 在下一写锁内前滚，snapshot 只锁并拒绝 pending，不隐式改源。缺失/损坏必要恢复对象安全拒绝，不能假称 applied。公开 revision/cache 与 Fundwise 不变。DG-01 时跨年/旧后端保守读取历史；DG-02 已按实际前置 bar 收窄分年读取，旧式单文件与递归计算仍有明确保守边界。隔离验收不授权生产修复、迁移、切换或清理。

### DG-02：集中存储访问，保持旧后端契约

修改范围：`store.py`、`pool.py`、`daily_storage.py`、`limit_amount.py`、`limit_events.py` 和维护入口中的日线直接读写。只建立实际需要的窄操作：按键/范围/字段读取，按变更集合写入，读取覆盖与逻辑修订。

外部 API 签名和符号格式维持兼容。统一处理旧式与分年路径，修复 `status()` 对旧目录的单一假设；单证券查询不先全池枚举；coverage 不通过每次回读全部年份刷新。

读取校验按确定数据版本执行或复用，不直接删除重复键、非法值检查来换速度。迁移前先使旧后端通过相同入口，避免业务模块积累更多目录分支。

验收：公开日线、ETF、事件成交额、状态、导入与修复入口通过原契约检查；模拟分年布局不漏读、不重复；消费者不自行选择物理文件或拼接新旧后端。

DG-02 feature `6c85113` 已实现具体 Parquet 日线入口；公开 daily/research/ETF/status、稀疏事件 amount、限价 scope/轴、merge/enrichment、BaoStock、在线/离线/free-stockdb、quote、CLI 及实际维护读取已接入。完整单位/字段/NULL/日期 overlay 与校验、批次/版本/锁保持；跨稀疏年份预热与依赖后缀等值，混存/错误分区拒绝，coverage 正常仅读冷年 footer。666 单元测试 +18 子测试通过，2 个外部 TickStockPanel host 环境测试显式跳过；五年 P0 比对 82,772 事件、抽查 30 金额，峰值 RSS 298,508,288 字节、71.178 秒通过。见 [实现/入口/限制报告](data_remediation_dg02_implementation.md) 和 [精确源码/命令/结果摘要](evidence/data-remediation/20260927-dg02/validation.json)。协调者已审阅并复用此证据，快进集成 `3bfc857`；未重复执行已通过验证。

兼容性例外明确保留：不存在证券/年份的存在性探测、旧池全局 `asset_type` 缺失的 metadata-only schema 探测（证明不存在可能遍历全部 footer，协调者明确接受）、无 min/max 统计的日期列回退、旧式单文件整读/重写及完整替换/递归计算保守历史。没有删除重复键/非法值检查，也没有普通调用自动拆分或生产写入。DG-03 评估 schema metadata index 与完整增长后端；DG-05/06 继续处理字段依赖、递归收敛及公开逻辑版本，而非把这次入口收敛记作这些任务已完成。

### DG-03：完整候选后端与架构决策

在独立数据目录构建 DuckDB 日线事实候选。保存全部既有必需字段、日期事实及来源语义，明确原始扩展字段的保留方式；主键约束、索引和查询计划属于候选的一部分。候选只接收确定来源快照及同一变更集合，不成为第二个独立权威写入入口。

测试负载包含：全市场一天/60 自然日/五年，单证券长历史，稀疏事件金额关联，ETF，新增日、旧日修订、删除、批量回补和无变化重跑。进一步测试 1×/2×/5× 历史、更多证券与多轮更新后的排序/索引维护。合成增长仅说明压力，不作为实际增长预测。

比较事务提交、检查点、锁等待、恢复、磁盘总量与公开接口耗时。验证 DuckDB 原生进程读写约束和现有池锁能否满足消费方式；不假定多个进程可自由并发读写同一文件。

交付 `architecture-decision.md`：选择 DuckDB 表或年月 Parquet 的理由、负载权重、失败条件、必要索引、并发策略、schema 映射、迁移与回退成本。若候选不通过，先修补明确问题或测试备选，不以 9 列聚合成绩推动切换。

验收：全部关键字段/键符合契约，候选在完整负载上有收益，单证券退化被量化并处理；增长后热点操作不退回全冷历史扫描/重写。保留逐轮原始样本，不仅报告最佳值。

验收：目标消费区间 stale 经实际计算清除；summary/coverage/events/exceptions 与参考价、连板边界一致；剩余未知和非法记录有明确处理口径。Fundwise 真实窗口可运行；不能将 stale 清零等同于基础数据完整。

### DG-05：按依赖控制计算和传播

建立字段到输出的依赖表：局部字段、有限滚动窗口、前后有效会话、递归连板状态、当日市场/板块截面及规则适用范围分别处理。普通请求明确读取范围、列和前置状态，不反复扫描所有历史以恢复市场日历。

先按证券维护受影响状态，再将受影响日期与其他证券的有效结果组合成完整截面。递归停止条件比较完整状态与后续输入/规则，不只比较显示板数；有多个修订区间时分别传播。检查点缺失或边界不明时保留完整依赖后缀回退。

验收：固定输入、规则和维度快照，增量结果等于完整参考重算；覆盖插入、删除、缺失、上市/ST 边界、跨年、不连续修订和规则升级。数值误差按字段契约，键与离散状态精确一致。

### DG-06：逻辑版本、一致发布与 Fundwise 缓存

保留现有池锁和单日限价发布事务。补齐输入修订、规则版本、schema 版本、维度快照、发布代次之间的关联；物理压缩/重排不自动变成业务修订。计算后提交前检查输入版本；中途失败保持可识别的有效发布和待修复范围。

由 aspool 公开提供可查询的修订信息；Fundwise `regime/freshness.py`、`data/regime_events.py` 据实际日期/数据域依赖复用缓存。先完成上游可靠信息，再收窄下游失效，不直接取消已有保守检查。

ST 和板块继续沿用现有业务口径，记录所用快照。快照变化导致的历史结果更新有真实业务依赖，不能作为误失效直接压掉。历史时点 ST/成分能力另立业务需求。

验收：无关月份更新不使无依赖变化的历史缓存失效；金额修订、规则升级及维度变化准确传播；物理重编码不制造业务重算；跨日读取发现来源变化或未完成发布时不会发布混合结果。

### DG-07：全链路验证与受控切换

使用固定输入与确定维度快照，在旧后端和候选分别运行真实 DataPool/Fundwise 链路。按日期、证券比较键、全部公开字段、NULL、事件与汇总，不以聚合相等代替全字段迁移验收。

验证原 P0 字段投影、有界批次、事件金额关联及五年 RSS ≤ 2 GiB。补齐 ETF 与其他已识别消费者，不仅测 Regime。测试维护期间读写协调、连续批次、并发输入变化和取消。

在候选写入后提交前、派生中途、发布切换前后注入失败，验证重启、幂等续跑和恢复。生成切换清单：输入水位、最后增量、校验结果、权威读写入口、恢复点与回退方式。

切换流程：独立迁入 → 同输入影子核对 → 受协调追平最后增量 → 校验 → 切换权威入口 → 核验公开接口。旧后端停止独立写入。回退必须包含切换后的变更，或在限定写入状态下执行，不能把过期旧池直接恢复成当前生产池。

验收：全部契约和资源检查通过；回退/恢复实际演练成功；真实消费链路成功且有结果证据。候选不通过则继续使用已验证旧后端，保留明确整改项，不标记完成。

### DG-08：恢复点退役与例行维护

沿用 [保留方案](regime_data_retention_plan.md) 的逐对象用途清单，并补充当前发布、保留恢复点、变更重放链、运行任务、未结问题引用。恢复目标和证据价值决定保留期，固定天数只能作为附加条件。

普通无引用且可再生的报告可独立整理；旧日线归档、v7 库、迁移前后基线和未结来源证据分别满足退役条件。一个新的正确快照不自动替代修复前原始证据。

验收：清理清单有路径、大小、校验、原因与引用检查；删除后恢复能力仍满足目标；生产字段、发布和消费者读取不受影响。报告净释放量时扣除新基线，移动到同盘目录不计空间释放。

## 5. 资源与正确性验收矩阵

| 场景 | 必须证明 | 资源证据 |
|---|---|---|
| 无变化重跑 | 无业务修订、无额外 stale、缓存保持有效 | 读取/枚举范围、耗时、锁等待 |
| 新增一个交易日 | 旧事实未被误改，派生与发布完整 | 写入量、计算范围、临时磁盘与 RSS |
| 修订历史一天 | 精确传播，正确处理后续窗口/递归与市场汇总 | 扫描、重算及缓存失效范围 |
| 规则升级 | 在明确适用区间与参考结果一致 | 明确批量任务预算、进度与恢复点 |
| 一天/60 日市场读取 | 全字段与原契约一致，不通过删校验提速 | 当前参考中位 7.664/8.051 秒；完整候选目标暂设热缓存中位 ≤ 1 秒，DG-03 验证 |
| 单证券历史、ETF、稀疏事件 | 覆盖其他负载，结果相等 | 单列原后端与候选成绩；按消费者预算裁决退化 |
| 五年有界事件读取 | 字段投影、金额关联、批次完整 | 峰值 RSS ≤ 2 GiB；保留任务卡原验收证据格式 |
| 增长和多轮维护 | 热点成本不隐含依赖全部冷历史；索引/检查点成本可解释 | 1×/2×/5×、证券数、字段数、操作次数分别记录 |
| 失败恢复与清理 | 恢复链、版本、公开读取仍成立 | 实测恢复耗时和数据损失范围，与 DG-00 目标对照 |

公开读取 1 秒目标是建议性能门槛，尚未通过完整候选验证；若需要调整，应在比较前给出原因与新的消费预算，不在测试失败后静默放宽。P95、冷启动、更新、重建和恢复预算在 DG-00/DG-03 按业务窗口补齐；既有 2 GiB 门槛不能被维护任务未定义的预算替代。

## 6. 证据、提交与状态管理

每次执行使用独立 `run_id`；报告至少包含代码提交/工作区差异指纹、依赖版本、来源水位与快照、规则和维度版本、参数、开始结束时间、完整样本、通过/失败项及遗留问题。

仓库 `docs/evidence/data-remediation/<run_id>/` 保存可审查的小型摘要、差异、基准结果与恢复清单；大数据副本和原始候选留在独立数据目录，通过清单引用，不提交进 Git。大文件是否可再生、清理条件也需记录。

建议按可回退单元提交：

1. 契约、恢复基线说明与观测；
2. 变更记录与无变化行为；
3. 统一访问边界及旧后端兼容；
4. 完整候选后端与选型证据；
5. 依赖传播、发布修订；
6. Fundwise 配套适配（在 Fundwise 仓库单独提交并记录兼容版本）；
7. 影子联调、迁移/回退工具与结果；
8. 恢复点退役与维护说明。

生产修复、schema/布局迁移、算法口径变化和报表删除分别记录，不能混成一笔不可解释的操作。每项任务只有在对应验收证据齐备后从“待实施”变为“已验收”；发现失败则记录实际状态及下一步，不以文档完成替代工程完成。
