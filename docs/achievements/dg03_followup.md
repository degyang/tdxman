## 问题与交付目标

全局 DuckDB 原型在 5×、89,311,935 行时，保留主键/索引的整日原子提交在 SQL 1 GB 下失败；单线程反事实也失败。月度 Parquet 原型读取和恢复已验证，但有效提交复制 933,507,072 字节 catalog。1× 单行修订观测写入约 964 MB，整日无变化重跑约 24 秒。这些是下一任务要消除的实际成本。

交付同一月后端的事务发布实现、独立协议审查、完整成本和故障证据。以已固定 DG-03 原始源及不可变前缀复用现有字段/读取证据；DG-07 再以 DG-04 实际修复后的输入版本完成影子追平。

## 实现顺序

1. 从现有 `CandidatePool.apply` 提取由调用者持有锁、连接及事务的共用变更核心，明确 BEGIN/COMMIT/错误保真责任；native 包装入口继续使用同一核心。
2. 以带完整主键/索引的 TEMP 表装入实际触碰月份，批量或索引比较语义差异。混合无变化输入保持冷月 manifest/path/hash 不变；facts-only 更新不安装 raw 月文件。
3. 先生成新的不可变月文件并 fsync，再在一个 live catalog 事务中提交 manifest、facts、coverage、stale、revision、audit。所有公开读遵守同一池锁和版本检查；重试身份、提交已成功但响应丢失的判定明确记录。
4. 保存备份引用集合、WAL 状态和旧版本保留语义。未引用 part/work 形成可审查清单，接入 DG-08 保留与清理流程。

## 验收与证据

- 原始完整字段、键、单位、NULL、显式 clear/delete、ETF/事件与公开错误契约符合现有基线；仅变化路径触发必要局部验证。
- before/after part fsync、before/after COMMIT 使用真实子进程 SIGKILL；raw/facts/coverage/stale/revision/audit 必须全部旧或全部新。首次只读重开及存在 WAL 的恢复实际执行。
- 实际多进程 writer/reader 和 writer/writer 使用受控握手；非空事件迭代遇到版本变化拒绝继续。验证旧版本与迁移到新目录的恢复引用、哈希和可读性。
- 原固定预算：维护 1 线程、SQL 1 GB、RSS 3 GiB 守卫；公开 daily 512 MB/2 线程，五年事件 RSS ≤2 GiB。保留实际各路径的有效线程配置。
- 同一 1×/2×/5× 源量验证整日 7,266 行原子变更、单行修订、跨月回补/删除、混合无变化、facts-only、12 轮修订/no-op。`catalog_copied_bytes=0`；冷 part 零重写、业务无变化 revision/stale 不变。实际记录 metadata/WAL/checkpoint 和 part 写量，验证增长后的热点成本，而非仅比较扫描量。
- 对逐行比较与更多证券的成本作实际压力检查；单证券历史访问、锁等待和备份/恢复预算在消费者验收时明确接受，不能从市场读取中位推断 P95。
- 原字段全量等值、旧 P0 和已成功测试复用；新事务协议对应的崩溃、WAL、写入和并发证据重新生成，因为旧 catalog rename 协议无法证明它。

## 调遣、集成和后续依赖

复杂存储实现和独立协议审查分别使用 Orca Astra/high，最高 effort 为 high；代码 owner 负责新变更的验证，协调者审阅证据与源码绑定，不重复 agent 已通过的测试。重型操作使用一个串行槽位，独立审查只读进行。实验数据根与生产分离，生产准入在 DG-07 统一消费接线、影子结果和恢复门通过后判定。

DG-05 派生增量依赖及 DG-06 逻辑版本/缓存整改可继续依托现有存储边界推进。DG-07 还需新鲜可信的板块成分快照、真实阶段与主线管线结果；DG-08 的旧副本退役依赖实际恢复与切换验收。本任务完成不自动等同于这些任务完成。
