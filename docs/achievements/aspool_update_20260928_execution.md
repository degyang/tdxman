## 当前故障处理机制与 tick 对照

日更默认每最多 500 只股票提交一个事务，内部提交分组不是业务发布批次。网络读取失败按参数重试；事实冲突和数据库写事务不自动重试。组内任一校验失败则整组回滚，已成功提交的组保留。

本次事件修正是显式 ops 维护，续跑是人工重新调用 CLI；当前没有自动事件修正或自动续跑机制。单证券冲突仍会中断后续全部更新。用户指出同一源事件的新旧差异应进入更新逻辑，这一意见成立：单纯隔离所谓“冲突”不足以修复日更语义。重新运行时相同源记录按差异判断跳过，源读取本身仍会发生。

核对本地 tick-stock-panel `d71cafc`：

- [kline_sync.py](../../../projects/tick-stock-panel/backend/app/services/kline_sync.py) 的 `sync_adj_factor`（495–609 行）按证券和日期合并，`keep="last"` 使本次成功获取的值覆盖旧值；源读取失败记录并保留旧值，继续其他分组。这里同步的是因子记录，没有本项目这套原始事件一致性拒绝逻辑。
- [repository.py](../../../projects/tick-stock-panel/backend/app/tickflow/repository.py) 的 `_optimistic_upsert_partition`（2243 行起）对日线同样保留最后输入，同值合并结果跳过物理重写。
- [daily_pipeline.py](../../../projects/tick-stock-panel/backend/app/jobs/daily_pipeline.py)（390–424、490–510 行）默认近期 15 天因子窗口，返回的证券交给 enriched 重算。其 affected 是本次返回的证券，不等于已严格完成字段差异检测；派生可能重算该股票全部日期，因子文件也仍整体合并替换。

据此确定后续修正规则（本次尚未实现）：

1. 同一可信来源、相同业务键且字段合法的新值，作为正常 UPSERT；真正变化才触发依赖重算。不能仅因与旧值不同而中断。
2. 日线与事件变化分别计算依赖：参考价、因子、MA20、连板和受影响日期的市场汇总在一致事务中更新。近期修订自动处理，不要求人工先改原始事件；超出明确预算的历史修订进入显式维护。
3. 抓取失败与字段非法分别报告，保留旧数据；不让一个证券阻断其他独立证券。修订不应混入失败列表。
4. 空响应不代表撤回。tick 的 keep-last 合并也不自动删除未返回旧记录；本次两个地址核验后的显式事件维护不能冒充通用撤回判定机制。
5. 采用其“成功新值覆盖、依赖重算、失败保留”的业务语义，继续使用 SQLite 局部差异写入，不复制整文件替换和受影响证券全历史重算的物理实现。

上面的规则是修正方向，当前已实现的仅为迁移事件编号/单位兼容修复；不能将运行库已人工恢复宣称为自动修订能力完成。
