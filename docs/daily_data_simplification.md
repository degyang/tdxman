# 日线与派生数据精简决策

日期：2026-09-28。状态：按用户最新约束收敛目标设计；尚未迁移生产存储或删除旧接口。股票数据以 SQLite 为目标，性能与生产切换尚未验证。业务只做局部更新，不再设计业务批次、修订发布体系；全量导入、重建和规则升级通过外部 ops 脚本维护。

落地入口：[四表实施计划](sqlite_four_table_implementation_plan.md)；迁移与接口依据：[系统评估](sqlite_migration_api_assessment.md)；新增多模型/日周月要求：[Regime 模型模板](regime_model_template_design.md)。

## 目标结构与日常更新

```text
tdxman/data/stocks.sqlite
├── daily_bars              未复权日线，主键 (symbol, trade_date)
├── corporate_actions       除权事件与独立来源因子记录
├── daily_features          pre_close、必要 ST/交易状态、涨跌停及连板
└── market_daily_summary    日/周/月公共市场特征与统计
```

股票业务库最终为上述四张表，包含必要的除权资料，不在图外另留一套因子业务表。corporate_actions 以 record_kind 区分原始事件和独立累计因子锚点，择定有效来源后计算复权 K 线，不重复乘两份因子。不再设置 coverage、exceptions、revisions、publication 业务表。指数和 ETF 属于各自的数据域，不计入这四张股票业务表；市场交易日历及基础证券目录复用既有公共资料，不另复制进股票库。

参考 tick 的单次事件因子口径：可直接取可靠源，也可由事件及参考价计算；因子按股票/生效日期稀疏保存于 corporate_actions，计算出的累计因子也在同表作为可再生列保存。普通交易日沿用此前有效值，不新增因子表。已导入累计因子不得当单次因子再次累乘，详见[实际调用链对照](sqlite_migration_api_assessment.md#31-对照-tick-的除权与因子链2026-09-28-补充)。

market_daily_summary 保留表名，键扩展为 (frequency, period_key, scope)，支持 D/W/M 公共特征；周/月只更新实际受影响周期，不由每个模型重扫全年股票。日特征聚合与真实周期股票收益分别定义。模型模板、参数及结果由 Fundwise 保存，详见模板设计，不新增股票业务表。

“Regime 落表”具体指上述公共市场特征落在第四张表；不同模型的评分、强弱/阶段状态同样持久保存，但属于 Fundwise 的应用结果存储。两者不混称为一张股票业务表。

采用 tick 日线合并的核心做法：按证券/日期键合并，返回数据覆盖同键已有值，无实际变化不写入。正常同步从该证券已有数据末端取小范围重叠到当前日；已知缺口按明确日期局部补取，不因缺口或首次无历史就自动启动多年导入。批量网络请求和有界读取分块是实现手段，不产生业务 batch_id。

源接口失败或未返回某行不表示删除；缺失字段不自动清空已有值。明确修正字段才更新，清空和删除须显式表达。tick 本身仍有因子变化重算历史、历史补齐扩大重建等分支；这里只采用其局部合并/no-op 行为，不照搬整史重写。对应实现见 tick `backend/app/tickflow/repository.py::append_daily` 与 `services/kline_sync.py`。

## ST：保存当日事实，避免套用当前名称

核对本地 `Projects/tick-stock-panel`：`backend/app/price_limits.py` 的判定是名称转大写后包含 `ST`；`pipeline.py` 从 instruments 按 symbol 关联该标记。`services/market_mainline.py::load_risk_warning_symbols` 明确说明维表是无历史版本的当前快照，Regime 使用该集合过滤历史范围。它覆盖 ST/*ST/S*ST 的名称识别，但没有完整解决历史戴帽、摘帽。

有可靠当日 name 即可判断 ST，无需为此单独建表或维护第二套相同事实。历史 name 只是当前名称回填时，不能据此判断历史 ST；已有来源的日期 ST 标记可在 daily_features 中保留可空 is_st 及来源，没有依据则为 NULL。可靠当日名称变化时刷新对应判定，不允许缓存标记与名称各自变更。

原设计 security_daily_facts 与 limit_events 合并为 daily_features，主键同为 (symbol, trade_date)。参考昨收就是 pre_close，没有另一个“参考昨收”概念。daily_features 统一保存有效 pre_close 与来源，公开日线 JOIN 返回。trading_status 不是涨跌统计的必需字段；仅作为可选源字段保留，用于过滤已确认停牌占位行及已有消费者兼容，缺行与确认停牌仍按同一统计分支处理，不推导或补齐一套交易状态历史。

没有 K 线但有可靠源日期事实时，daily_features 可以有一行，限价/连板字段留空；统计只消费实际成交记录，不因特征行存在就制造 K 线或涨跌停事件。源字段与计算字段分列，在同一个局部事务维护，重算不能清掉已有源事实。

## 删除独立结构，保留最少必要信息

| 当前概念 | 目标处理 | 留下的信息 |
| --- | --- | --- |
| 日线 coverage | 取消重复维护的独立覆盖表；从有索引的日线查询，确有开销再缓存 | 日期范围、行数；范围不代表连续无缺口 |
| 限价 coverage | 合并到每日统计/计算状态，不再单独维护一套结果 | 已知、未知、无价格限制、无效数量；不另设发布完成状态 |
| exceptions | 取消业务必读表；判定状态合并进 daily_features，详细诊断进运行日志 | limit_status 与必要原因码；无价格限制是正常状态 |
| revisions | 删除独立修订结构及输入版本/结果版本配对流程 | 事务快照保证一致读；受影响日汇总的更新时间用于缓存检查 |
| publication | 删除独立批次表、发布指针和每批历史结果副本 | 日线、日期事实、限价和汇总在同库事务内提交 |

`read_limit_coverage` 当前本来就是查询 batches/publication/staleness 的接口，并没有同名实体表。精简针对其底层重复状态和消费者调用，不虚构可删除的表。原始行是否存在，与派生结果是否可用必须分开表达。

限价状态至少区分已知、未知、无价格限制、无效。派生标志使用可空布尔值，未知不得写成 false；未获得完整输入也不得把统计零当作真实零。保留简短原因码即可，不要求消费者读取逐条诊断日志。

## 用局部变更回调与事务替代发布系统

普通写入使用单 writer，在一个 SQLite 事务内比较输入并写入实际差异，然后同步调用局部变更处理函数，计算对应限价与汇总，成功一起提交；失败一起回滚。下载在事务外完成。没有实际变化就不触发回调、不改更新时间、不失效缓存。

这里的事件就是包含证券、日期、变化字段的进程内函数调用，不引入消息中间件、事件历史表、异步投递/重试体系。交易成功后通知本进程缓存；Fundwise 等独立进程按依赖日期的汇总更新时间检查缓存，读取多表时使用同一数据库快照，不能只靠可能丢失的进程通知。更新时间只在实际相关变化后更新，并保证同日连续更新可区分，不承担发布代次含义。

回调按字段走少数明确分支：成交额修正更新该日汇总和金额相关缓存；价格、参考价、ST 等修正更新当日限价，并沿该证券后续实际 K 线传播连板状态，直到完整递推状态重新一致且后面没有另一处待处理变更。只对结果受影响的日期更新市场汇总，允许读取该日市场截面；禁止因此重算其他股票的全部历史。

多个库不做联合原子发布，股票限价链所需输入与结果放在 stocks.sqlite。新增除权事件只更新对应复权计算/缓存；按发生日期局部处理参考价依赖，不重写原始历史。长期或全量重算放到外部 ops 脚本，在维护窗口协调消费者，不给业务接口加 full/rebuild 模式或失败后的自动全库回退。

## 历史断点与补数

用户明确指定：证券存续期间历史缺数据与已确认停牌采用完全相同的涨跌统计逻辑。两者都不计入当天上涨、下跌、平盘、涨跌停家数和成交统计，不进入对应比例的有效样本分母；不生成假 K 线或涨跌停事件。连板状态冻结，不增加板数，也不因缺数据或停牌本身清零；下一根实际 K 线继续判断，涨停则接续，否则断板。存在停牌占位行时同样排除，不能因数据库中有行就计为平盘。

是否由来源确认停牌只作事实追溯，不改变上述统计分支；缺行不另计为限价 unknown/invalid，不因此阻断当日汇总或 Regime 的限价输入。未知判定仅用于实际有交易数据但缺少参考价等必要条件的记录。上市前、退市后和非市场交易日不能算成停牌缺口。使用上一根有效原始 K 线时须考虑间隔内除权，优先采用复牌日可靠参考价；参考价无法确定时保留未知，不直接搬用旧收盘制造涨停结论。该约定允许有缺口时按已有有效样本统计，补数后统计值相应修正，不宣称缺口期间已覆盖真实全部交易。

补数会触发与普通更新相同的回调：补入日限价、该证券后续连板、结果变化日期的市场汇总局部更新。例：周一涨停、周二缺行、周三涨停，暂按周三二板；补入周二普通交易后，周三改为首板；若补入周二涨停，周三改为三板。当前只保存最新结果，补数允许修正历史统计，不维护多个历史发布版本。

## 迁移顺序与当前边界

1. 实现四张业务表及必要索引，除权资料纳入 corporate_actions；先实现局部合并、无变化不写和同事务变更回调。
2. 旧接口先从新字段生成兼容返回值；Fundwise 的适配器再改为直接读取日统计及事件。兼容阶段不复制一份新的权威数据。
3. 更新 Fundwise 对 coverage/exceptions 能力、批次一致性和 freshness 的依赖；改用同一读取快照、日期汇总状态及局部更新时间。旧客户端在旧后端过渡；v3适配层也不制造 batch_id，协调升级消费者后切换。
4. 消费者切换验证通过后，删除旧批次、发布指针和重复覆盖/异常实体；最后按恢复保留策略清理历史诊断及副本。

当前生产仍通过 publication 选择结果，异常还参与连板边界处理。直接 DROP 或停止写入会破坏读数与重算；此次只落地设计与推进约束，未执行删表。新增验证聚焦局部更新/no-op、断点冻结、补数后连板传播、间隔除权、同事务失败回滚和跨进程缓存检查。缺口语义是明确变化，新结果应对照新口径完整参考计算，不要求与旧算法错误地逐值相等；其余迁移字段复用既有验证。
