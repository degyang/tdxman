# 公共质量接口交付后的执行计划

2026-09-28。状态：规划，尚未执行本计划的数据写入、远端任务或配置切换。用户已告知 Fundwise 正在接收上游交付；消费方接收不等于生产启用。

## 目标与基线

下一阶段交付一个闭环：真实数据具备质量解释，新日线和历史补数能局部更新派生，Jakarta 获得相同成品，Fundwise 按实际可用输入运行并明确呈现剩余缺口。

沿用 [公共质量回执](../achievements/up_rg_feature_public_quality.md) 的接口，不扩表、不新增批次平台。代码已推送至 `f29ecfb`；真实库尚未安装两个新增质量列。此前 Jakarta 全量复制已经完成，但对应旧结构。此前全历史 Regime 综合分仅 1,727 日可用且为 known_subset，周期阶段无可用结果；质量说明字段本身不会消除这些限制。

本阶段验收以实际窗口、真实写入、消费结果为准，不以代码测试通过代替生产就绪。历史事实能补多少取决于可核实来源，不预设全历史可完全修复。

## 执行顺序

### 1. 固定联调窗口与维护边界

主开发负责。先读取 Fundwise 本轮接收结果，确认实际安装工件、请求字段、日期窗口与预热范围，避免重复设计其适配层。

- 默认以现有成功联调的 2026-09-01 至 2026-09-24 为消费窗口，加入消费方实际需要的前驱/预热；用户没有新范围要求时无需重新询问。7 月 3 日和 6 日保留作质量对账样本。
- 原始数据、派生及指数的最新可用日分别核对；9 月 24 日只是此前观测末日，不能称为当前应有最新日，也不能把缺少日线自动等同于市场休市。
- 记录当前库结构、文件状态、活动读写者、恢复路径与可用空间。保持单一权威写入端，本阶段仍由本机维护，Jakarta 接收只读成品。
- 制定一致恢复点和恢复步骤，核对所需空间。报告放 `.local/reports/`，恢复材料放 `.local/recovery/`，不混入 `data/`。

完成标准：有明确的安装标识、计算窗口、输入末日及维护清单。发现消费端字段契约问题先局部修复，不等整库历史补齐。

### 2. 启用质量字段，并跑通真实日更

主开发负责。先执行可恢复的显式结构升级，只为联调窗口及固定质量样本初始化新增汇总字段。其余历史保持 NULL，不在普通读取中自动补算。

- 使用 `scripts/ops/backfill_summary_quality.py`，明确起止日期；新增列不触发源事实或全历史逐股重算。
- 核对两种 scope 的 UNKNOWN/INVALID 原因对账和候选池分母等式。区分未计算 NULL、已计算无异常、无可判定样本。
- 确认真实日线采集调度实际调用 SQLite 局部更新入口，避免只在测试中走新路径、日常任务仍写旧文件。核对采集结果到字段归一化、差异判断、派生和汇总的完整调用链。
- 对一个实际有变化的近期窗口执行日更，记录新增、修订与不变数量，受影响日期、逻辑读取量、耗时和 RSS；无真实新数据时明确记录，不伪造新增日。
- 同窗口重复一次检验幂等性，数据库业务行和时间戳不变化。新增日、故障回滚等已有测试直接复用；只有实际调用链缺陷或新代码变化才增加相应验证。

完成标准：真实库能读出联调窗口的质量字段；实际日更接入正确，无变化不写，普通业务没有隐藏全历史更新。此时可先交付 Fundwise 日频消费验证。

### 3. 优先修复影响当前 Regime 的输入

主开发拥有源事实写入及派生逻辑。来源核查可以作为 Jakarta 的独立辅助任务，但必须有明确输出文件、证券/日期范围和不写运行库的约束；本规划不直接启动 worker。

修复优先级：消费窗口及必要预热 → 已知问题样本 → Fundwise 明确需要的更长历史。先按原因和日期聚合已有汇总定位，再查对应证券明细；不以解决缺口为由直接全市场、全历史重新下载。

1. **参考昨收与除权依据**：查既有日线、除权事件/因子和源接口能否提供可验证的日期事实。跨缺口的上一条收盘不能直接冒充当天参考昨收。
2. **历史 ST 依据**：追溯旧导入来源与日期。`raw_fallback:legacy_unspecified` 只是候选值；核实后才升为可信事实，不能使用当前名称倒填历史。
3. **连板前驱、指数窗口**：在前两项修复后检查连续性与指数交易日边界，判断 Fundwise 周期输入是否仍不可用。

每个修复包明确证券、日期、变化字段、事实依据和预计后缀，通过局部更新接口原子写入。遇到 60 日或时间预算边界，转为显式 ops 分窗方案，不抬高日常业务预算以隐式吞掉全历史任务。

完成标准：交付修复前后缺口变化、受影响汇总/连板结果和仍不可补原因。以 Fundwise 实际分数及阶段适用性判断业务改善；若关键事实仍无来源，明确这一阻塞，不将 known_subset 宣称为完整结果。

第 2、3 步若能在同一维护窗口完成，合并形成一次成品后再同步；来源调查长期无结论时，先发布质量字段可用的成品，不让它无限等待历史修复。

### 4. 同步经过验收的成品到 Jakarta

主开发负责源成品和复制入口，Jakarta 辅助负责接收端空间检查、文件校验与安装验收；职责不交叉。远端耗时任务必须运行在 tmux 中并保留可观察的进度及退出状态。

- 先修正复制入口的证据参数：当前 `copy_full_data.sh` 固定引用 `20260928-derived-result.json`。库已变化后，必须使用与本次成品哈希对应的新完整性证据及新清单，不能沿用旧哈希结论。
- 维持完整成品复制方案，不在本轮临时引入活库页增量、双向写入或通用同步平台。源端和接收端各自校验的内容只做必要一次；相同哈希的成品可复用已有完整性验收。
- 接收前核对当前实际空间，包括运行库、接收库、恢复点和写入临时空间。此前余量约 4.1 GiB 是旧观测，低于单个约 9.2 GB 股票库，不能据此直接启动新全量接收。
- 若空间不足，先确定扩容或已验收且允许回收的材料；不得覆盖唯一可用库、删除唯一恢复点，或擅自改为原地更新活库来节省空间。
- 接收目录保持隔离，按清单校验后再受控安装。`data/` 只保留运行数据；新结构、两种 scope、质量样本和数据末日一致。

完成标准：新成品的代码/安装标识、文件哈希和公开读取结果均有接收端回执。此前成功复制的 8,157 文件记录保留为旧验收，不改写成新版已同步。

### 5. Fundwise 联调收口，再决定扩大范围

Fundwise 负责消费适配、缓存失效与页面/接口呈现，上游提供字段与可复用证据。避免两边分别扫描全市场重建质量汇总。

- 核对无质量字段、已装但未算、已算但有缺口三种状态；收到空值不能当成零缺口。
- 消费窗口读取新质量解释；修复后相应缓存失效，无变化时不重复计算。
- 本机与 Jakarta 对相同输入窗口的质量计数、晋级分母及 Fundwise 结果一致。直接复用未受影响的旧快照、分页和内存验收，不重跑全套。
- 写明生产配置是否已切换、哪个数据根正在使用、存在何种剩余缺口。切换是单独记录的部署动作，不把需求接收当作切换完成。

完成标准：日频流程在已声明的数据质量边界内可持续运行，下一次新增日和历史修订有固定入口、同步步骤与恢复方式。
